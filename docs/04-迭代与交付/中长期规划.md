# 中长期开发规划

## 1. 规划口径

本文用于承接 Sprint 13 之后的中长期开发节奏。规划对象仍遵循本目录统一口径：

- Epic 表示能力域。
- Backlog 表示可跟踪交付项。
- Sprint 表示时间盒。
- Release 表示版本发布判断。

本规划不是冻结需求。每个 Sprint 开始前仍需按当前风险、验证结果和用户反馈做一次轻量取项确认。

## 3. 未来 5 个 Sprint 主线

### Sprint 14：评估结果驱动配置优化

承接 Sprint 13 的 EvaluationRun / Result 最小闭环，重点补齐异步状态、失败重试、评估指标汇总、结果导出、Config Revision 对比和失败样本到配置草稿的优化入口。

成功标准：研发和测试能从一批评估结果定位失败样本、查看相关配置差异，并生成一个可复核的配置优化草稿。

### Sprint 15：真实 Provider 生产化接入

重点处理真实 LLM、Embedding、Rerank、Dense、Sparse、Graph Provider 的凭据配置、脱敏展示、连通性诊断、限流诊断和副本重建恢复。

成功标准：测试环境可以在不泄露凭据的前提下完成 Provider 复测，并把失败原因落到可排障的报告里。

### Sprint 16：知识库治理与文档质量

围绕文档解析质量、异常 Chunk、批量重解析、批量重建索引、知识库健康概览和 Chunk 排除标记展开。

成功标准：知识库负责人可以看到影响 QA 效果的文档质量问题，并能批量触发治理动作。

### Sprint 17：稳定性与观测

补齐 QARun、IngestJob、Provider 调用指标，增加慢链路诊断、错误摘要、健康面板、任务幂等和备份恢复演练。

成功标准：出现慢查询、Provider 失败或任务重复执行时，研发能通过平台数据定位问题，而不是只看后端日志。

### Sprint 18：协作与治理增强

面向多人协作补齐配置发布记录、变更说明、回滚确认、QA Run 分享评论、审计报表、数据保留策略和有效权限解释。

成功标准：配置变更、QA 诊断结论和权限判断都能被团队复核，并能形成可审计记录。

## 4. 取项原则

- 每个 Sprint 优先交付一条可验证主链路，不把多个复杂子系统塞进同一轮。
- P1 Backlog 优先于 P2；P2 只有在主链路完成且风险可控时进入实现。
- 每个 Sprint 至少保留一个脚本级验证入口，前端变更必须保留 `npm run build` 作为最小检查。
- 真实外部 Provider 失败不阻塞 local/mock 验收，但必须记录诊断结果和环境限制。
- 文档、接口、数据模型和实现如果出现冲突，以 PostgreSQL 业务真值、后端执行契约和可验证脚本为优先。

## 5. 风险与观察点

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 真实 Provider 环境不可用 | V1.2 生产化接入延迟 | 保留 local/mock 验收，真实环境用诊断报告单独复测 |
| EvaluationRun 范围膨胀 | Sprint 14 无法闭环 | 先做同步或轻量异步执行，不引入复杂调度平台 |
| 文档质量治理规则过多 | Sprint 16 变成规则平台 | 优先覆盖空 Chunk、重复 Chunk、解析失败和权限异常四类高价值问题 |
| 观测指标过细 | Sprint 17 维护成本升高 | 只采集 QARun、IngestJob、Provider 调用三类关键指标 |
| 协作治理过重 | Sprint 18 偏离内部工具定位 | 只做记录、评论、责任人和回滚确认，不做复杂审批流 |
| 真实解析范围膨胀 | V1.4 难以稳定验收 | 首轮只覆盖 txt、md、pdf、docx，OCR、复杂版面还原和表格语义增强后置 |
| 外部检索组件不可用 | V1.4/V1.5 真实链路验证受阻 | 保留 local/mock 启动能力，但真实链路脚本必须能记录依赖限制并在环境可用时复测 |
| LLM API 响应不稳定 | 解析图谱、生成回答和回放结果不稳定 | 固化 OpenAI-compatible 契约，记录请求摘要、响应错误和模型配置快照 |
| 回放绕过当前权限 | 历史结果泄露或复跑越权 | 回放只复用上下文，不复用授权结果；Evidence 读取和复跑都按当前权限二次校验 |

## 6. V1.4 / V1.5 近期主线

### Sprint 19：真实解析与 Chunk 入库

替换上传后的占位解析链路，优先支持 txt、md、pdf、docx；同时固化真实 LLM API 与 Embedding API 的 OpenAI-compatible 契约，为后续向量、图谱抽取和生成链路打基础。

成功标准：上传真实文件后，P07 能看到真实 Chunk 内容、页码或章节、token 数和 parser metadata；解析失败不会伪装成功。

### Sprint 20：真实多副本写入与入库状态

将 Chunk 和 Embedding 写入 Milvus，将 Chunk 文本与过滤字段写入 OpenSearch，基于真实 LLM 抽取实体关系并写入 Neo4j，同时把 Index Sync 升级为真实执行型 Worker。

成功标准：一个真实文档完成入库后，可以分别从 PostgreSQL、Milvus、OpenSearch 和 Neo4j 追溯同一批 chunk_id。

### Sprint 21：真实检索与生成链路

P09 QA 调试基于真实 Milvus、OpenSearch、Neo4j 和 LLM API 执行 Dense、Sparse、Graph、Fusion、Rerank、Permission Filter、Generation 和 Citation，不再依赖 local/mock 成功路径。

成功标准：一次 QA Run 的 Trace 能展示真实 Provider 调用和 PostgreSQL 回表裁剪，Answer 由真实 LLM 基于授权 Evidence 生成。

### Sprint 22：真实回放、复跑与对比

P10 历史回放带回原 query、sourceRunId、configRevisionId、overrideParams、retrieval channels 和原诊断摘要；复跑后能比较原结果、新结果和配置差异。

成功标准：回放创建新的 QARun，并能对比答案、证据、引用、Trace 指标和配置差异；历史读取和复跑均不绕过当前权限。

## 7. V1.6 / V1.7 后续主线

### Sprint 23：真实文档 RAG 端到端链路

基于 `docs/examples/` 中的真实样例文档，打通上传、解析、Chunk、Embedding、多副本索引、QA 查询、授权 Evidence 和 Citation 的主链路。

成功标准：用户能基于真实上传文档完成一次 QA，并看到可追溯 Evidence、Citation 和 Trace；失败时能明确区分代码缺口、配置错误和外部 Provider 环境不可用。

### Sprint 24：真实 RAG 监控回放与验收硬化

补齐 P06/P07/P09/P10 的真实链路状态展示、回放复跑、差异对比、V1.6 端到端验收脚本和真实依赖复测记录。

成功标准：同一个真实文档 QA Run 能被回放复跑，并能对比答案、Evidence、Citation、Trace 耗时和配置差异；V1.6 验收脚本可作为发布前入口。

### Sprint 25：RAG 检索节点模块化配置

扩展 Query Rewrite、Multi Query、Dense、Sparse、Hybrid Fusion、Graph Retrieval、Rerank 和 Context Packing 的受控节点与参数配置，让 P08 更贴近真实 RAG 调参台。

成功标准：P08 能保存、校验并展示核心 RAG 节点参数，QARun 执行时能读取并在 Trace 中展示实际使用值。

### Sprint 26：RAG 配置评估与优化闭环

固化 QARun Pipeline Snapshot，并通过评估集对比不同 Pipeline 配置的命中、引用、答案质量、耗时和失败原因，形成可复核优化建议。

成功标准：研发能基于评估结果定位失败样本、查看配置差异，并生成一个不会自动上线的配置优化草稿。
