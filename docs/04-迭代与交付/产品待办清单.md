# 产品待办清单

## 1. 使用说明

- 本清单承接需求条目、技术任务、缺陷和优化项，是长期 Backlog，不等同于当前 Sprint 计划。
- Epic 是能力域，Sprint 是时间盒；一个 Sprint 可以包含多个 Epic 的 Backlog，一个 Epic 也可以跨多个 Sprint 完成。
- 每条 Backlog 应能映射到需求、原型、设计、测试或运维文档。
- 每个 Sprint 开始前，从状态为 Ready 或高优先级 Todo 的条目中选择本轮交付范围，写入 `sprints/` 下的对应 Sprint 计划。
- 每个 Backlog 完成后，同步更新本清单；每个 Release 发布前，再从本清单汇总范围、验收状态和遗留风险。
- 本清单是 Backlog 和 Epic 状态源；总览类文档只做索引和链接，不复制完整状态表。

## 2. 版本目标

V1.0 的开发目标是先完成“可运行、可配置、可追溯”的 RAG 调试平台最小闭环：

1. 本地工程可启动，前后端基础链路可验证。
2. 用户、知识库、文档、配置和 QA Run 有稳定数据模型与接口。
3. 文档入库、配置激活、QA 调试和历史查看可以形成最小闭环。
4. 真实 LLM / Embedding / 检索组件通过 Provider 抽象逐步替换 mock 能力。

V1.1 的目标是在 V1.0 可追溯基础上补齐 RAG 质量闭环：批量评估、结果沉淀、配置对比和从评估结果反推配置优化。

V1.2 的目标是推进真实 Provider 生产化接入和知识库治理：凭据配置、连通性复测、检索副本重建、文档质量检查和知识库健康概览。

V1.3 的目标是增强稳定性、观测和协作治理：运行指标、慢链路诊断、备份恢复演练、配置发布记录、协作审计和有效权限解释。

V1.4 的目标是补齐真实文档入库链路：真实解析、Chunk 切分、真实 LLM/Embedding API 接入、Milvus 向量写入、OpenSearch 文本写入、Neo4j 图谱构建和入库状态可见。

V1.5 的目标是补齐真实检索与回放闭环：QA 调试基于真实 Dense/Sparse/Graph/LLM 链路执行，并支持历史回放、复跑和差异对比。

V1.6 的目标是将真实 RAG 功能完全走通：基于真实文档完成解析、索引构建、检索查询、答案生成、监控诊断和历史回放复跑的端到端有效闭环。

V1.7 的目标是深化 RAG 模块化调优：丰富可配置检索节点、节点参数、Pipeline 快照和评估对比能力，使配置中心贴近真实 RAG 优化流程。

V1.8 的目标是在现有 RAG 调试与治理能力上增加应用化封装：把治理后的知识库和 Pipeline 发布为可被外部 Web 应用调用的 RAG 应用，提供受控对话接口、应用级凭据、会话记录、调用审计和质量回流。Sprint 35 已完成前端工程化、P13 真实 Runtime 试运行、反馈回流、调用→QA 跳转和真实 Provider E2E 验收硬化。

E22 是 V1.7 后的内部功能增强，不建立新的 Release，目标是强化知识库治理工作流：把已有质量摘要、批量治理、Chunk 排除、索引重建和评估回归能力串成 P05/P06/P07 可操作闭环。

E23 是 V1.9 的能力域，目标是补齐图快照保留策略和配置管理入口：让 `graph_snapshots`、`graph_chunk_refs` 和 Neo4j 中的图快照数据具备可配置的保留、清理、审计和页面可见能力。

E24 是 V1.9 的能力域，目标是增强文档解析能力：先收口当前解析依赖，再评估 MarkItDown 对 DOCX/XLSX/PDF 的统一 Markdown 输出能力，并评估 MinerU 作为复杂版式、表格和 OCR PDF 的可选增强链路。

E27 是 V1.9 的能力域，目标是补强 RAG App 运行治理与接入可见性：调用进入 Runtime 后立即生成 running 调用记录，P13 可监控运行中调用并查看 API 调用文档，同时以直接打回方式处理超过应用级并发上限的请求。

E25 是 V1.8 的新增能力域，目标是补齐 RAG 应用化封装：外部应用通过 App API Key 调用统一对话接口，每次回答仍复用 QARun、Evidence、Citation、Trace、权限裁剪和评估回流，不把平台改造成自由工作流或公网匿名聊天产品。

E26 是 V1.8 的功能完善与验收硬化，目标是以前端真实动作为驱动，验证 RAG App、App Runtime、反馈回流、调用审计、QA 历史回溯和真实 Provider 链路均使用真实服务与真实数据。已完成。

E30 是后续架构演进能力域，目标是在现有项目上收口文档库、知识库、智能应用三层模型：文档库作为源文件资产层，知识库作为知识加工与 Chunk 检索层，智能应用作为外部 API 发布层；同步完成权限模型、版本与 ParseRevision、BindingRevision、Chunk 生命周期、删除影响分析和 QA 历史回溯改造。

E31 是后续多模态 RAG 演进能力域，目标是在现有文档库、知识库和 QA 链路上支持图片内容。第一阶段采用图片转视觉文本 Chunk 的方式融合现有 Dense/Sparse/Graph、Evidence 和 Citation；第二阶段预留多模态 embedding、Visual Retrieval、以图搜图和区域级 Citation。

## 5. 状态定义

- Todo：已识别但尚未进入近期交付。
- Ready：信息足够，可进入后续 Sprint。
- In Progress：当前正在实现或联调。
- In Review：实现完成，等待代码、文档或验收复核。
- Done：代码、文档和验证结果已回填。
- Blocked：存在依赖、环境或需求阻塞，暂不能推进。
- Cancelled：因需求变更或优先级调整，已取消开发。

## 6. Sprint 取项规则

- Sprint 计划只选择本轮要交付和验证的条目，不复制完整 backlog。
- P0 且状态为 Ready 的条目优先进入 Sprint。
- 如果 Sprint 中发现待办范围过大，应拆分为更小条目后再推进。
- Sprint 结束后，将完成状态回写到本清单，并补充新增缺陷或后续任务。
