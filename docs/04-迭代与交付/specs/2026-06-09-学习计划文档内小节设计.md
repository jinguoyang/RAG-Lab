# 学习计划文档内小节设计规范

> 本文是学习计划“文档包含学习小节”结构的设计规范，作为本次实现依据。本文属于设计归档；当前迭代状态仍以产品待办清单、Sprint 总览和 Release 总览为准。

## 1. 目标

学习小节用于拆分单份文档的教学内容，解决长文档单课时内容过多的问题。学习计划应先确定文档及文档顺序，再针对每份文档规划一个或多个学习小节，以支持碎片化学习。

本次实现必须满足：

- 学习小节是文档的附属属性，不能跨文档引用。
- 学习计划不再维护顶层 `sections`。
- 课堂顺序固定为“文档顺序 + 文档内小节顺序”。
- 短文档可以只有一个小节，长文档可以拆分为多个小节。
- 删除文档时，其下全部小节随文档一起删除。

## 2. 数据契约

学习计划使用以下嵌套结构：

```json
{
  "planId": "plan-001",
  "documents": [
    {
      "documentId": "doc-001",
      "title": "安全操作规程",
      "relevance": 0.92,
      "abilityGroup": "安全作业",
      "difficulty": "基础",
      "sections": [
        {
          "sectionId": "section-doc-001-001",
          "title": "作业前风险识别",
          "learningObjective": "能够识别作业前必须检查的风险项",
          "evidenceChunkIds": ["chunk-001", "chunk-002"],
          "keyPoints": ["检查作业环境", "确认防护措施"],
          "checkpointCriteria": ["能够说出主要风险项", "能够选择正确的处置动作"],
          "teachingScript": {
            "opening": "string",
            "explanation": "string",
            "scenario": "string",
            "interactionQuestions": ["string"],
            "summary": "string"
          },
          "teachingQualityScore": 0.85,
          "estimatedMinutes": 8,
          "required": true
        }
      ]
    }
  ]
}
```

约束如下：

- `documents` 数组本身表示学习文档顺序，不再由独立 `readingOrder` 决定课堂顺序。
- 每份入选文档必须包含非空 `sections`。
- 小节不再包含 `sourceDocumentIds`；其所属文档由父级确定。
- `evidenceChunkIds` 只能引用父级文档的 Chunk。
- `sectionId` 在单个学习计划内必须唯一。
- 平台草稿、ex-app 本地保存结果和课堂冻结快照均使用同一嵌套结构。
- 新结构不保留顶层 `sections`，避免形成两个状态源。

## 3. 学习计划生成

平台先生成入选文档及其顺序，再逐文档生成小节。

生成规则：

1. 模型必须结合单份文档的完整结构、标题层级和内容密度规划小节。
2. 小节按可验证的文档内学习目标组织，不能按 Chunk 数量机械拆分。
3. 短文档允许生成一个小节；长文档可按概念、职责、流程、风险或操作阶段拆分多个小节。
4. 每个小节只能使用当前文档的 `documentId`、Chunk 和正文证据。
5. 模型输出无效或调用失败时，规则回退也必须逐文档生成小节，不能按能力组合并文档。

程序校验必须拒绝或过滤以下内容：

- 小节引用其他文档的 Chunk。
- 入选文档没有有效小节。
- 小节缺少标题、学习目标或 Checkpoint 标准。
- 同一计划中出现重复 `sectionId`。

## 4. ex-app 编辑与保存

学习计划审核页以文档为一级编辑单元：

- 文档按当前数组顺序展示，并支持调整顺序。
- 每份文档下展示其学习小节，并支持调整文档内小节顺序。
- 小节标题、学习目标、预计时长和是否必修沿用现有编辑能力。
- 删除文档时直接删除整个文档对象，不再单独清理顶层小节关联。
- 新增文档时，必须为该文档生成或创建至少一个小节后才能保存计划。

ex-app 后端将嵌套小节随 `documents` JSON 一并保存，不新增数据库表或独立 JSON 状态源。保存和更新请求移除顶层 `sections` 与 `readingOrder`。

## 5. 课堂执行

ex-app 创建课堂会话时，将已保存计划的嵌套 `documents` 写入 `courseSnapshot`：

```json
{
  "courseSnapshot": {
    "planId": "plan-001",
    "version": 1,
    "documents": []
  }
}
```

平台收到快照后执行以下处理：

1. 按 `documents` 数组顺序遍历文档。
2. 按每份文档的 `sections` 数组顺序遍历小节。
3. 将结果展平为课堂内部执行序列。
4. 为每个内部执行项补充父级 `documentId` 和文档标题。
5. `currentSectionIndex`、完成数量和总小节数均基于展平序列计算。
6. 当前小节检索和引用仅限所属文档及其 `evidenceChunkIds`。

课堂 API 不接受顶层 `courseSnapshot.sections`。缺少文档、小节结构非法、小节无有效证据归属或 `sectionId` 重复时，应返回明确的请求错误。

## 6. 兼容边界

本次采用完整嵌套方案：

- 新生成草稿、新保存计划和新课堂快照只输出嵌套结构。
- 不继续写入顶层 `sections` 或 `readingOrder`。
- 不实现长期双结构同步。
- 对当前开发环境中已保存的旧计划，可在读取入口执行一次内存归并：仅当文档没有 `sections` 且旧顶层小节可唯一归属于某一文档时，将其挂到对应文档。
- 无法唯一归属的跨文档旧小节不得静默拆分，应提示重新生成学习计划。
- 兼容读取不得回写或继续传播旧结构；计划再次保存后必须成为新结构。

## 7. 影响范围

本次仅修改与学习计划嵌套小节直接相关的内容：

- 平台学习计划 DTO、提示词、解析、校验和规则回退。
- 平台课堂快照校验、顺序展平、证据限定和进度计算。
- ex-app 后端学习计划 DTO、保存更新和课堂快照构造。
- ex-app 学习计划审核页的类型、状态和文档内小节编辑展示。
- 对应平台与 ex-app 测试。
- 与本契约直接相关的接口设计说明。

本次不新增数据库表、不调整题库归属、不改变课堂状态机状态集合，也不重构无关模块。

## 8. 验收标准

- 平台生成的每份文档均带有至少一个有效小节。
- 任一小节只能归属于一个父级文档，且不再包含 `sourceDocumentIds`。
- 长文档测试样例能够生成多个小节，短文档测试样例允许生成一个小节。
- ex-app 可按文档展示、编辑和排序小节。
- 调整文档顺序后，课堂按新的文档顺序执行。
- 调整文档内小节顺序后，课堂按新的小节顺序执行。
- 删除文档后，其小节不会出现在保存结果或课堂快照中。
- 平台拒绝包含顶层 `sections` 或无效嵌套引用的课堂快照。
- 平台后端相关单元与集成测试通过。
- ex-app 后端相关单元与集成测试通过。
- ex-app 前端 `npm run build` 通过。
- 文档修改通过 `git diff --check`。
