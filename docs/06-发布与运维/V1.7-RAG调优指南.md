# V1.7 RAG 调优指南

本文是 V1.7 发布后的 RAG 参数调优和人工复核指南，属于发布与运维层的活文档。

## 1. 使用边界

本指南用于 V1.7 受控 RAG Pipeline 的人工调参复核。P08 负责生成和保存配置草稿，P09/QARun 负责固化当次运行快照，P10 负责基于评估对比观察效果并生成优化建议。

优化建议只作为草稿来源，不自动激活生产配置。任何参数调整都应先通过 EvaluationRun 回归，再由配置管理员在 P08 复核并发布。

## 2. 参数字典

| 参数 | 节点 | 推荐范围 | 主要影响 | 常见风险 |
| --- | --- | --- | --- | --- |
| `queryRewrite.rewriteStrategy` | Query Rewrite | `none`、`semantic`、`keyword`、`hybrid` | 改善问题表达和召回稳定性 | 过度改写会偏离原始意图 |
| `multiQuery.queryCount` | Multi Query | 1-4，复杂问句可到 6 | 提升复杂问题召回覆盖 | 查询数越多，延迟和成本越高 |
| `denseRetrieval.topK` | Dense Retrieval | 5-30 | 提升语义召回数量 | topK 过高会引入噪声 |
| `denseRetrieval.scoreThreshold` | Dense Retrieval | 0.2-0.8 | 过滤低置信语义候选 | 阈值过高可能漏召回 |
| `sparseRetrieval.topK` | Sparse Retrieval | 5-30 | 增强关键词和专有名词召回 | 关键词噪声可能增加 |
| `sparseRetrieval.fusionWeight` | Sparse Retrieval | 0.1-0.6 | 控制稀疏候选在融合排序中的权重 | 权重过高会压制语义候选 |
| `graphRetrieval.graphDepth` | Graph Retrieval | 1-2，谨慎到 3 | 扩展实体关系上下文 | 深度过高会放大无关路径 |
| `graphRetrieval.graphExpansionLimit` | Graph Retrieval | 10-80 | 控制图扩展候选上限 | 上限过大会增加延迟 |
| `fusion.candidateLimit` | Fusion | 10-80 | 控制进入后续 Rerank 的候选池 | 候选池过小会影响召回 |
| `rerank.topN` | Rerank | 3-20 | 控制最终证据候选数量 | topN 过高会增加上下文压力 |
| `contextPacking.maxContextTokens` | Context Packing | 2048-12000 | 控制生成上下文预算 | 过高会增加成本并稀释证据 |
| `contextPacking.chunkWindow` | Context Packing | 0-2 | 保留相邻 Chunk 补充上下文 | 窗口过大可能带入无关内容 |
| `generation.temperature` | Generation | 0-0.4 | 控制答案稳定性 | 过低可能过于保守，过高可能漂移 |

## 3. 调参流程

1. 在 P10 选择失败或低质量样本加入评估集，确保样本覆盖典型查询、长尾问题和权限裁剪场景。
2. 在 P08 基于当前 active revision 复制草稿，只调整一组相关参数，例如召回参数或上下文参数。
3. 用新配置触发 EvaluationRun，观察命中、引用、答案质量、耗时和失败原因。
4. 对比 QARun 的 Pipeline Snapshot 与 nodeParamSnapshot，确认评估结果来自预期配置。
5. 若 P10 生成优化建议，先查看关联样本、建议参数、预期影响和风险，再决定是否复制到 P08 草稿。
6. 发布前保留变更说明和回滚计划，至少记录评估对比结论和仍未覆盖的风险。

## 4. 快照与评估对比

每个 QARun 会保存 `pipelineSnapshot` 和 `nodeParamSnapshot`。评估对比应优先使用 QARun 快照，而不是重新读取当前 ConfigRevision，避免历史结果被后续草稿或配置变更污染。

P10 的配置效果对比优先查看以下指标：

- `hitCount`：候选融合后的命中数量，过低时优先检查 topK、scoreThreshold、multiQuery 和 graphDepth。
- `citationCount`：可引用证据数量，过低时优先检查权限裁剪、Context Packing 和 citationPolicy。
- `latencyMs`：整体耗时，过高时优先收紧 multiQuery、graphExpansionLimit、candidateLimit 和 rerankTopN。
- `failureReason`：失败归因，answer_mismatch 更偏生成和上下文问题，source_run_not_success 更偏执行链路或权限问题。

## 5. 常见诊断方向

- 低召回：先降低 `scoreThreshold` 或小幅提高 Dense/Sparse/Graph 的 `topK`，再观察 `hitCount` 是否提升。
- 引用不足：优先检查权限裁剪结果，再提高 `contextPacking.maxContextTokens` 或 `chunkWindow`。
- 答案漂移：降低 `generation.temperature`，并确认 Query Rewrite 没有改变用户原意。
- 图检索噪声：降低 `graphDepth` 或 `graphExpansionLimit`，保留 `mustFallbackToChunk`。
- 延迟过高：减少 `multiQuery.queryCount`、`fusion.candidateLimit` 或 `rerank.topN`，避免一次调整过多参数。

## 6. 发布注意事项

- 单次发布只调整少量参数，并保留原始 Revision 便于回滚。
- 配置发布前至少完成一次 EvaluationRun，并在发布记录中写明评估对比结论。
- 对优化建议保持人工复核，不能因为建议来自失败样本就直接激活。
