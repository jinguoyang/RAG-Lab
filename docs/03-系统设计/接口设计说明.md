# 接口设计说明

## 1. 文档目的

本文档定义 RAG 调试平台后端 API 的设计约定、接口清单、关键接口入参与出参、鉴权规则、错误模型和调用约束。

本文档面向前端联调、后端开发、测试验收和后续 OpenAPI 细化使用。本文档为接口草案级设计，不替代最终代码中的 OpenAPI Schema、字段校验实现和权限矩阵配置。

### 2.2 覆盖范围

本文覆盖以下接口域：

- Auth：登录、退出、当前用户
- Users / Groups：用户、用户组与组成员
- Knowledge Bases：知识库、概览、成员绑定、权限摘要
- Templates / Config Revisions：模板、Pipeline 校验、配置保存、激活、Diff
- Documents / Versions / Chunks：文档上传、版本、Chunk、重解析
- Ingest Jobs：作业查询、重试、取消
- QA Runs / QA History：单次调试、运行详情、历史查询、反馈、回放
- Graph / GraphSnapshots：图快照、实体搜索、关系路径、支撑 Chunk
- Evaluations：回归样本沉淀
- RAG Apps：应用定义、配置绑定、API Key 管理和调用审计
- App Runtime：外部 Web 应用对话调用和反馈回流
- Observability：运行指标、慢链路诊断、错误摘要、健康面板、Token 消耗、成本估算、备份恢复演练

### 2.3 非覆盖范围

- 不定义模型厂商、Milvus、OpenSearch、Neo4j 的底层 SDK 接口。
- 不定义数据库 DDL 和迁移脚本。
- 不定义完整 OpenAPI JSON / YAML 文件。
- 不定义公网匿名聊天产品；App Runtime API 仅面向受控外部 Web 应用。

## 3. 通用接口约定

### 3.1 协议与路径

| 项 | 约定 |
| --- | --- |
| 协议 | HTTPS，开发环境可使用 HTTP |
| 风格 | RESTful API |
| 基础路径 | `/api/v1` |
| 数据格式 | `application/json; charset=utf-8` |
| 文件上传 | `multipart/form-data` |
| 时间格式 | ISO 8601，例如 `2026-04-24T10:30:00+08:00` |
| ID 格式 | API 层统一使用 `...Id`，值为 UUID 字符串 |
| 字段命名 | 请求和响应使用 `camelCase`；数据库内部可使用 `snake_case` |

### 3.2 鉴权方式

- 登录成功后由后端签发访问令牌，后续请求通过 `Authorization: Bearer <token>` 传递。
- App Runtime 接口使用 `Authorization: Bearer <app_api_key>` 传递 App API Key，不复用后台用户登录态。
- 所有受控接口必须执行后端鉴权，前端按钮隐藏或置灰只作为交互优化。
- 未登录访问返回 `AUTH_UNAUTHORIZED`。
- 已登录但无权限访问返回 `AUTH_FORBIDDEN`，或在列表场景中直接过滤不可见资源。
- 权限判断遵循默认拒绝、Deny 优先、检索阶段和输出阶段双重裁剪原则。

### 3.3 请求头

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 受控接口必填 | Bearer Token |
| `Content-Type` | 是 | JSON 请求使用 `application/json; charset=utf-8`，文件上传使用 `multipart/form-data` |
| `X-Request-Id` | 否 | 前端生成的请求 ID，便于幂等和排障 |
| `X-Trace-Id` | 否 | 链路追踪 ID；未传时由后端生成 |
| `X-End-User-Id` | App Runtime 可选 | 外部应用侧终端用户标识，后端只作为会话归因和审计摘要 |

### 3.4 统一响应格式

成功响应统一使用以下结构：

```json
{
  "success": true,
  "data": {},
  "traceId": "trace-20260424-0001"
}
```

失败响应统一使用以下结构：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数不合法",
    "detail": "pipelineDefinition 至少需要启用一路检索",
    "fields": [
      {
        "field": "pipelineDefinition.nodes",
        "message": "Dense、Sparse、Graph 至少启用一路"
      }
    ]
  },
  "traceId": "trace-20260424-0002"
}
```

说明：

- `message` 面向前端展示，应稳定、简洁。
- `detail` 面向排障，可按环境控制是否返回。
- `fields` 用于表单或 Pipeline 校验的字段级错误。
- 响应中的 `traceId` 必须可关联后端日志。

### 3.5 分页、排序与筛选

分页查询统一使用 Query 参数：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `pageNo` | integer | 否 | 1 | 页码，从 1 开始 |
| `pageSize` | integer | 否 | 20 | 每页数量，建议最大 100 |
| `sortBy` | string | 否 | `createdAt` | 排序字段 |
| `sortOrder` | string | 否 | `desc` | `asc` / `desc` |
| `keyword` | string | 否 | 空 | 关键词搜索 |

分页响应统一结构：

```json
{
  "items": [],
  "pageNo": 1,
  "pageSize": 20,
  "total": 0
}
```

### 3.6 幂等与并发控制

- 文件上传、创建 QARun、重试作业等可能重复提交的接口，应支持 `X-Request-Id` 或业务幂等键。
- Revision 激活、文档 active version 切换等高风险操作应记录审计日志。
- 对需要防止覆盖的更新接口，可在后续实现中使用 `updatedAt` 或 `version` 做乐观并发控制。

### 3.7 接口稳定性与组件解耦原则

- 接口字段应面向业务语义设计，不面向某个前端 UI 组件结构设计。
- 后端 DTO 与前端页面 ViewModel 必须允许分离，前端通过 Adapter 转换后再传给页面组件。
- 接口不得暴露具体 UI 组件名称，例如 Card、Drawer、Canvas、NodeCard 等。
- `pipelineDefinition` 是业务契约，应描述阶段、节点类型、参数、约束和 Provider 能力，不应描述画布坐标、颜色、图标等纯展示信息。
- QA Run 接口应返回可转换为 Trace、Candidate、Evidence、Citation、Metrics 的稳定业务数据，不应绑定某个调试页面布局。
- 检索、模型、图谱等后端组件替换时，应尽量保持接口业务语义稳定，只在 Provider / Adapter 层处理实现差异。

### 6.5 切换文档 active version

- 路径：`POST /api/v1/knowledge-bases/{kbId}/documents/{documentId}/versions/{versionId}/activate`
- 描述：将指定版本设为文档 active version。
- 权限要求：`kb.document.upload`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `confirmImpact` | boolean | 是 | 前端二次确认标记，必须为 `true` |
| `reason` | string | 否 | 切换原因 |

#### 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `documentId` | string | 文档 ID |
| `activeVersionId` | string | 新 active version ID |
| `previousActiveVersionId` | string | 原 active version ID |
| `auditLogId` | string | 审计日志 ID |

#### 设计约束

- `failed` 状态版本不得激活。
- 目标版本必须满足知识库索引能力配置的最小检索就绪门槛：解析成功，标记为 `requiredForActivation` 的 Dense / Sparse / Graph 副本状态为 `success`，未启用能力为 `not_required`。
- Config Revision 或本次 QARun 的 Sparse / Graph 开关只决定运行时是否调用对应检索 Provider，不决定文档版本激活前是否应维护 OpenSearch 或 Neo4j 副本。
- 切换后不删除旧版本和旧 Chunk，历史 QA 仍可追溯旧版本。
- 后续检索副本清理或重建通过异步作业处理。
- 切换后若旧图快照不再匹配当前 active version，必须标记为 `stale`，后续 QA 默认不使用该快照。

### 6.6 Pipeline 校验

- 路径：`POST /api/v1/knowledge-bases/{kbId}/config-revisions/validate`
- 描述：基于 `pipelineDefinition` 和 Provider 能力声明执行后端校验。
- 权限要求：`kb.config.manage`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `pipelineDefinition` | object | 是 | 受约束 Pipeline 定义 |
| `baseRevisionId` | string | 否 | 基线 Revision，用于差异提示 |

#### 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `valid` | boolean | 是否通过校验 |
| `errors` | array | 阻断性错误 |
| `warnings` | array | 非阻断性提示 |
| `normalizedPipelineDefinition` | object | 后端规范化后的定义，可用于保存 |

#### 最小校验规则

| 规则 | 失败错误码 | 说明 |
| --- | --- | --- |
| 至少启用 Dense、Sparse、Graph 中一路 | `PIPELINE_NO_RETRIEVAL_ENABLED` | 全关闭时不可保存和运行 |
| `permissionFilter` 必须存在且在生成前 | `PIPELINE_PERMISSION_FILTER_REQUIRED` | 安全护栏不可绕过 |
| `citation` 必须来自授权 Evidence | `PIPELINE_CITATION_INVALID` | Citation 不得引用未授权内容 |
| Query Rewrite 若启用必须在 Retrieval 前 | `PIPELINE_STAGE_ORDER_INVALID` | 阶段顺序固定 |
| Graph Retrieval 输出必须回落 Chunk | `PIPELINE_GRAPH_CHUNK_FALLBACK_REQUIRED` | 图结构不能直接作为证据 |

- 路径：`POST /api/v1/knowledge-bases/{kbId}/config-revisions`
- 描述：保存新的配置版本，保存后默认不生效。
- 权限要求：`kb.config.manage`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `pipelineDefinition` | object | 是 | 受约束 Pipeline 定义 |

#### 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `configRevisionId` | string | 新 Revision ID |
| `revisionNo` | integer | 知识库内递增版本号 |
| `status` | string | 默认 `saved` |
| `validationSnapshot` | object | 保存时校验摘要 |

#### 设计约束

- 保存前必须执行后端 Pipeline 校验。
- 保存不等于生效；后续 QA 默认仍使用当前 active revision。
- `pipelineDefinition` 不保存画布坐标、颜色、图标等 UI 展示字段。

#### 历史 Revision 复用入口

- 路径：`POST /api/v1/knowledge-bases/{kbId}/config-revisions/drafts/from-revision`
- 描述：从指定历史 Revision 复制 `pipelineDefinition`，生成新的草稿，供 P08 继续编辑、校验和保存。
- 典型入口：P08 Revision 历史中的“复制为草稿”操作，适用于复用 archived Revision 或 active Revision 的配置内容。
- 请求字段：`sourceRevisionId` 为必填；`remark` 可选，用于记录草稿来源说明。
- 响应字段：返回新草稿的 `configRevisionId`、`revisionNo`、`status = draft` 和复制后的 `pipelineDefinition`。
- 设计约束：该接口不得修改源 Revision 的 `status`、`activated_at`、`deactivated_at` 或历史审计字段；草稿保存为正式 Revision 前仍必须经过后端 Pipeline 校验。

- 路径：`POST /api/v1/knowledge-bases/{kbId}/config-revisions/{revisionId}/activate`
- 描述：将指定 Revision 设为知识库 active revision。
- 权限要求：`kb.config.manage`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `confirmImpact` | boolean | 是 | 二次确认标记，必须为 `true` |
| `reason` | string | 否 | 激活原因 |

#### 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `activeConfigRevisionId` | string | 新 active Revision ID |
| `previousActiveConfigRevisionId` | string | 原 active Revision ID |
| `activatedAt` | string | 激活时间 |
| `auditLogId` | string | 审计日志 ID |

#### 设计约束

- 只有 `saved` 状态的 Revision 可以从页面发起激活；`invalid`、`draft`、`archived`、未通过校验或不属于当前知识库的 Revision 不允许激活。
- 激活操作必须在同一事务中更新旧 active Revision、新 active Revision、`knowledge_bases.active_config_revision_id` 和审计日志。
- 旧 active Revision 默认转为 `archived`；如需复用历史配置，应通过“从历史 Revision 生成草稿”入口创建新草稿，不回退旧 active。
- 已创建的历史 QARun 仍指向执行时锁定的 `configRevisionId`，不随 active 切换改变。

### 6.9 创建 QARun

- 路径：`POST /api/v1/knowledge-bases/{kbId}/qa-runs`
- 描述：基于 active revision 或指定 revision 发起单次 QA 调试，并创建异步运行记录。
- 权限要求：`kb.qa.run`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `query` | string | 是 | 原始问题 |
| `configRevisionId` | string | 否 | 指定运行版本；缺省使用当前 active revision |
| `overrideParams` | object | 否 | 仅本次有效的临时覆盖参数 |
| `sourceRunId` | string | 否 | 回放来源 run ID |
| `remark` | string | 否 | 实验备注 |

#### 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `runId` | string | QA Run ID |
| `status` | string | 创建后默认为 `queued` |
| `kbId` | string | 知识库 ID |
| `configRevisionId` | string | 本次锁定的配置版本 |
| `query` | string | 原始问题 |
| `createdAt` | string | 创建时间 |
| `statusUrl` | string | 状态轮询地址 |
| `detailUrl` | string | 运行详情地址 |

#### 设计约束

- 创建时必须锁定本次使用的 `configRevisionId`。
- 临时覆盖参数不得修改 active revision，必须写入 `overrideSnapshot`。
- Dense、Sparse、Graph 至少启用一路，否则拒绝运行。
- Graph 结果必须回落到授权 Chunk / Evidence 后才能进入上下文。
- 未授权 Chunk 不得出现在 answer、evidence、citations 中。
- 部分检索通道失败但仍能生成答案时，状态应为 `partial`，并在 trace 中说明降级原因。
- MVP 阶段统一采用异步执行：创建接口只返回 runId、queued 状态和轮询地址；前端通过状态接口轮询阶段进度，通过详情接口读取最终结果。
- WebSocket 或 Server-Sent Events 可作为后续优化，不改变创建接口契约。

- 外部响应不得暴露未授权 Chunk 正文、被裁剪候选、Provider 密钥或系统提示词。
- 每次有效 App/Key 调用都必须先写入 `AppInvocation.status = running`，完成后更新为 `success` 或 `failed`；成功时助手消息必须关联 `runId`。
- `streaming` 是输出适配，不替代 QARun，也不绕过 Invocation 审计。

### 6.21 图片视觉文本抽取 Provider 约定

图片文件不新增独立业务 API，仍通过文档库上传、解析和知识库绑定接口进入系统。后端图片解析 Worker 调用 `VisionTextProvider`，接口契约如下：

| 项 | 约定 |
| --- | --- |
| 默认模型 | `mimo-v2.5` |
| 默认 endpoint | 可配置，真实接入建议为 `https://api.xiaomimimo.com/v1/chat/completions` |
| 默认鉴权头 | `api-key`，可通过配置切换为 Bearer 兼容模式 |
| 图片传参 | OpenAI-compatible `image_url` 内容块，`url` 为 `data:{mime};base64,...` |
| 支持格式 | `jpg/jpeg/png/gif/webp/bmp` |
| 大小限制 | base64 编码字符串超过 50 MB 时返回图片过大类错误，不调用外部 Provider |
| 安全摘要 | 可记录模型名、MIME、文件大小、`image_tokens`；不得记录 API Key、base64 或原图二进制 |

图片解析成功后，现有文档、Chunk、QA 和 Citation 接口返回的 metadata 可包含：

| 字段 | 说明 |
| --- | --- |
| `sourceModality` | 固定为 `image` |
| `sourceMimeType` | 原始图片 MIME |
| `sourceFileSize` | 原始图片大小 |
| `visionModel` | 视觉抽取模型，例如 `mimo-v2.5` |
| `imageTokens` | Provider usage 中的图片 token 数，可为空 |
| `region` | 第一阶段固定为 `full` |

## 9. 安全与权限约束

### 9.1 列表接口可见性

- 知识库列表只返回当前用户可见的知识库。
- 文档列表只返回当前用户具备 `kb.document.read` 权限的文档摘要。
- QA 历史列表默认返回发起人自己的记录；具备 `kb.qa.history.read` 的用户可查看知识库范围内记录。
- Dense、Sparse、Graph 检索请求中的权限过滤条件必须由后端根据角色、用户组、ACL、密级和 `ChunkAccessFilter` 生成，不接受前端传入的主体级过滤条件。
- 当检索 Provider 不支持主体级过滤时，后端必须先计算授权 Chunk 范围，再限制召回范围。

### 9.2 Chunk 与 Citation 安全

- Chunk 正文读取必须具备 `kb.chunk.read`。
- QA Evidence 和 Citation 只能基于授权 Chunk 构建。
- 被权限裁剪的候选只能以数量、状态或裁剪原因进入诊断摘要，不得暴露正文。
- 图检索命中的实体、关系和社区不得直接作为 Citation。
- 历史 Evidence 快照读取必须按当前用户权限二次校验；无权限时只能返回来源摘要、hash、脱敏状态或“当前无权查看”提示。
- 如采用全文 Evidence 快照，后端必须加密存储；高安全部署可使用脱敏或 hash-only 策略。

### 9.3 高风险操作审计

以下操作必须写审计日志：

- 创建、停用知识库
- 添加、修改、移除知识库成员
- 上传文档、重解析文档、切换 active version
- 保存、激活 Config Revision
- 取消 QARun 或 IngestJob
- 修改 QA 人工反馈
- 创建、禁用或删除 RAG App
- 生成、删除或轮换 App API Key

### 9.4 App Runtime 安全

- App API Key 明文只在生成时返回一次，后端只保存 hash 和 keyPrefix。
- App Runtime 只能访问当前 key 归属 App 绑定的知识库和配置版本。
- `conversationId`、`messageId` 和 `runId` 都必须校验归属关系，禁止跨 App 枚举读取。
- 外部响应只返回安全摘要；完整 Trace、候选淘汰详情和内部配置差异仍在平台登录态下查看。
- App Runtime 的 Citation、Evidence 和 Answer 必须沿用 QARun 的权限裁剪结果。

#### 9.4.1 App API Key 生命周期

| 阶段 | 规则 |
| --- | --- |
| 格式 | 管理端生成固定前缀 `rlak_` 的高熵随机字符串；外部调用只通过 `Authorization: Bearer <app_api_key>` 传递 |
| 存储 | PostgreSQL 仅保存 `sha256(plaintext_key)`、`key_prefix`、状态、过期时间和创建审计字段，不保存明文 |
| 展示 | 明文只在创建响应中返回一次；列表、详情、调用记录和审计日志只展示 `keyPrefix` |
| 轮换 | 轮换采用“生成新 Key + 外部切换 + 删除旧 Key”的双 Key 窗口，不原地修改旧 Key 明文 |
| 删除 | 删除会物理移除 Key 行；历史调用记录继续保留，但 `app_invocations.api_key_id` 置空 |
| 过期 | `expires_at` 为空表示不过期；非空且早于当前时间时统一按 `APP_API_KEY_INVALID` 拒绝 |

#### 9.4.2 隔离粒度

| 边界 | 规则 |
| --- | --- |
| App 级 | API Key 只能解析到所属 `app_id`，不能由请求体切换 App |
| 知识库级 | Runtime 使用 App 绑定的 `kb_id` 和默认 Revision；不得接受外部传入 `kbId`、主体权限或检索过滤条件 |
| 会话级 | `conversationId` 只在当前 App 内有效，跨 App 复用按资源不可见处理 |
| QARun 级 | 外部响应只返回 `runId` 摘要；完整 Trace、Evidence 快照和候选详情仍要求平台登录态和知识库权限 |
| Citation 级 | Citation 必须来自 QARun 已授权 Evidence；被治理排除、权限裁剪或副本 stale 的 Chunk 不得进入外部 Citation |

#### 9.4.3 限流与配额策略

第一版不在 Sprint 32 实现完整限流，但 Sprint 33 的实现策略固定为应用级令牌桶优先：

- 粒度：以 `app_id` 为主限流键，必要时叠加 `api_key_id` 作为排障维度；暂不以 `endUserId` 作为强一致配额键。
- 算法：短窗口突发控制采用令牌桶；日/月配额采用调用统计聚合，不用滑动窗口承担所有计费语义。
- 拒绝点：超过限流或配额时，在创建 QARun 前返回 `RAG_APP_QUOTA_EXCEEDED`；超过 `metadata.runtimeLimits.maxConcurrent` 时返回 `RAG_APP_CONCURRENCY_EXCEEDED`。两类拒绝都不进入队列，避免占用同步 blocking / SSE 连接。
- 审计：被限流的调用应写入 `app_invocations.status = failed`、`error_code = RAG_APP_QUOTA_EXCEEDED`、`latency_ms` 和安全请求摘要。
- 运行中监控：通过限流和并发检查后，应立即写入 `app_invocations.status = running`；调用结束后更新同一条记录，不追加第二条成功记录。
- 兼容：限流失败不得暴露 Key 是否存在、App 名称、知识库名称或 Provider 内部错误。

#### 9.4.4 Runtime 错误与审计字段

| 场景 | HTTP | 错误码 | 审计要求 |
| --- | --- | --- | --- |
| Key 无效、过期、已删除或所属 App 已删除 | 401 | `APP_API_KEY_INVALID` | 未解析到 App 时不写 App 调用审计；不得泄露 Key 状态 |
| App 停用或归档 | 409 | `RAG_APP_DISABLED` | 已解析 App/Key 时写 failed invocation |
| 知识库停用 | 409 | `KB_DISABLED` | 写 failed invocation，保留 `api_key_id` 和 `app_id` |
| 无可运行 Revision | 409 | `RAG_APP_NO_RUNNABLE_REVISION` | 写 failed invocation，便于管理端定位配置问题 |
| QARun 创建冲突 | 409 | `QA_RUN_CONFLICT` | 写 failed invocation，不创建助手消息 |
| 限流或配额超限 | 429 | `RAG_APP_QUOTA_EXCEEDED` | 写 failed invocation，不执行 QARun |
| 并发上限超限 | 429 | `RAG_APP_CONCURRENCY_EXCEEDED` | 写 failed invocation，不排队，不执行 QARun |

`app_invocations.request_summary` 只允许保存 `queryLength`、是否携带 `conversationId`、是否携带 `inputs` 和 `responseMode` 等安全摘要；不得保存 App API Key、完整用户问题、Provider 密钥、系统提示词或未授权 Chunk 正文。

### 9.5 员工培训三方接口

员工培训三方接口统一使用 `Authorization: Bearer <app_api_key>`。平台根据 Key 反查所属员工培训 App、知识库和默认配置版本；请求体不得携带 `appId`、`kbId` 或 Provider 配置来切换调用对象。

| 能力 | 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- | --- |
| 计划草稿生成 | POST | `/api/v1/training/plans/drafts` | 有效 App API Key | 根据岗位和简介生成学习计划草稿候选 |
| 文档查询 | GET | `/api/v1/training/documents` | 有效 App API Key | 查询当前 App 知识库可加入学习计划的文档 |
| 题库草稿生成 | POST | `/api/v1/training/questions/drafts` | 有效 App API Key | 按 `documentIds` 逐文档生成题目草稿；题库真值由 ex-app 保存 |
| 主观题评分 | POST | `/api/v1/training/post-quizzes/subjective-grading` | 有效 App API Key | ex-app 提交题干、答案、rubric 和证据，平台返回 5 分制评分 |
| 课堂会话 | POST | `/api/v1/training/classroom/sessions` | 有效 App API Key | 创建员工课堂会话 |
| 课堂事件 | POST | `/api/v1/training/classroom/sessions/{sessionId}/events` | 有效 App API Key | 提交开始、继续、追问、答题等课堂事件 |

约束：

- 学习计划最终名称、文档顺序和员工绑定由 ex-app 保存；平台不再把学习计划审批作为进入课堂的前置条件。
- 题库记录、题目审核、题目修改、课后测验抽题/提交、题目异议和异议处理均由 ex-app 保存和处理；平台接口不要求传入 ex-app 本地 `questionId`。
- 题目仍需 ex-app 管理员审核发布后才能进入 ex-app 本地正式题库。
- 课后测验只从 ex-app 本地已发布题库抽题；默认抽 5 题，按选择、判断、主观题 4:4:2 近似分配。
- 课后测验开始前必须校验对应课堂学习进度已完成；若进度元数据包含已学习文档列表，还会校验当前 `documentId`。
- 课后测验通过后会在 ex-app 本地课堂会话元数据中记录 `completedDocumentIds`，作为文档级学习完成标记。
